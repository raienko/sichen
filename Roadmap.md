# Core codebase roadmap

Last audited: 2026-10-19 · Previous: 2026-09-26

Scope: the whole repository — Expo SDK 57, React Native 0.86, React 19.2

This file holds **open work only**. Decisions and their reasons are in [docs/adr](docs/adr/README.md). Reference plans are in [docs/plans](docs/plans) — [CI and EAS](docs/plans/ci-and-eas.md), [agents](docs/plans/agents.md), [tooling](docs/plans/tooling.md) and [references](docs/plans/references.md) — and the security plan is [docs/security/plan.md](docs/security/plan.md). Estimates are for one engineer.

## Priorities

| Priority                              | Meaning                                                                           | Scheduling rule                                                                                 |
| ------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **P0 — Foundation**                   | A blocker for safe feature work, reliable collaboration, or reproducible delivery | Complete before broad product/UI expansion. Steps with the same dependency may run in parallel. |
| **P1 — Product-ready core**           | Required for a coherent, accessible first product flow and trustworthy previews   | Complete before calling the component system or preview channel production-ready.               |
| **P2 — Release readiness**            | Required before store submission or justified by measured product needs           | Start after real product routes and signed preview builds exist.                                |
| **P3 — Continuous/product-triggered** | Recurring work or capabilities that need a concrete product requirement           | Schedule by cadence or only when the listed trigger exists.                                     |

Follow step numbers within a priority unless the dependency column explicitly permits parallel work. A step is complete only when its “Done when” evidence exists; creating a file or dispatching a remote job is not completion by itself.

## Closed since 2026-09-26

- **01 Freeze the trustworthy baseline** — `yarn verify`, pinned Node/Yarn (`.nvmrc`, `engines`, `packageManager`), and the Code quality workflow reproduce every check on a clean runner.
- **02 Decide repository role** — application boilerplate; [ADR 0005](docs/adr/0005-application-boilerplate.md) defines internal exports, ownership, dependency direction, routes and app versioning. `package.json` is private and ESLint enforces upward import boundaries.
- **03 Add required GitHub CI** — Code quality: formatting, lint, types, unit tests with a coverage summary, secret scan, Expo Doctor, web build, native bundles, Storybook build, dependency review and CodeQL; SHA-pinned actions, timeouts, least-privilege tokens. Triggers are manual until branch protection is turned on.
- **04 Make builds and dependencies deterministic** — Node/Yarn pinned; the EAS project id is omitted from the config when unset; unused direct dependencies removed and implicitly used ones (`@expo/fingerprint`, `@expo/env`) declared; native binaries cached by fingerprint.
- **E2E foundation** (not a numbered step) — Maestro flows on iOS, Android and web from one file, unified `testId()` selectors, `isE2E` / `isDebug`, and repack-based builds.
